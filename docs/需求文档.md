# 室内空气质量监测系统 — 需求规格说明书

---

## 1. 项目概述

### 1.1 项目背景

开发一套室内空气质量监测系统，通过部署在家庭各房间的空气质量检测设备，实时采集 AQI、PM2.5、NO₂、SO₂、O₃ 等关键指标数据，供用户通过微信小程序查看和管理。同时为运维人员提供基于 Web 的管理面板。

### 1.2 数据链路总览

```
检测设备（模拟器）→ HTTPS → 云服务器 → Redis 缓冲 → MongoDB（原始数据存储）
                                                          ↓
                                              定时任务（每日 01:05）→ MySQL（日统计）
                                                          ↓
微信小程序 ← HTTPS ← Flask API（查询 MongoDB / MySQL）
运维面板 ← HTTPS ← Flask API
```

### 1.3 部署环境

| 项目 | 说明 |
|------|------|
| 云服务器 | 阿里云 ECS，Ubuntu |
| 公网 IP | 47.109.191.13 |
| API 端口 | 5000（Nginx 反向代理 443 HTTPS） |
| CI/CD | Jenkins，端口 8080 |
| 源码仓库 | GitHub → Gitee 同步 |

## 2. 用户角色

### 2.1 普通用户（微信小程序端）

使用微信小程序查看家中空气质量数据，进行简单的设备管理和个性化设置。

**典型用户画像：**
- 家庭住户，关心居住环境的空气质量
- 非技术用户，需要直观的数据展示
- 希望通过手机随时查看家中情况

### 2.2 管理员（Web 监控面板）

通过浏览器访问监控面板，管理模拟器运行状态、查看系统运行指标、进行报警演示。

**典型用户画像：**
- 系统运维人员
- 负责模拟器启停、数据链路监控
- 需要实时掌握系统运行状态

### 3.3 系统功能

| 编号 | 功能模块 | 功能描述 | 优先级 |
|------|----------|----------|--------|
| S-001 | 数据接收 | API 接收模拟器上报的 JSON 数据，验证 API Key 和 MD5 摘要，存入 Redis Stream | P0 |
| S-002 | 数据缓冲 | Redis Stream 作为消息队列缓冲上报数据，削峰填谷 | P0 |
| S-003 | 数据持久化 | consumer.py 从 Redis Stream 消费数据，批量写入 MongoDB（每批 100 条或每 5 秒刷新） | P0 |
| S-004 | 日统计聚合 | 每天 01:05 自动从 MongoDB 聚合前一日数据（日均 AQI、最高 AQI、日均 PM2.5），写入 MySQL daily_summary 表 | P0 |
| S-005 | 心跳上报 | 模拟器每隔 5 秒通过 Redis 上报心跳状态（running / stopped），记录数据发送量 | P0 |
| S-006 | 死信队列 | 消费失败的数据自动转入 Redis `dead_letter_stream`，防止数据丢失 | P1 |
| S-007 | 数据重传 | 模拟器发送失败时缓存到本地 `failed_data_cache.json`，后续重试发送 | P1 |

## 4. 非功能性需求

### 4.1 性能要求

| 编号 | 指标 | 要求 | 说明 |
|------|------|------|------|
| P-001 | 数据上报频率 | 每 5 秒 1 条/设备 | 模拟器默认配置 |
| P-002 | 模拟器并发量 | 支持同时运行 ≥7 个模拟器 | 对应 7 个设备 |
| P-003 | API 响应时间 | ≤500ms（P99） | 小程序端接口 |
| P-004 | 历史数据查询 | ≤2s（查询 24h 数据） | MongoDB 全量扫描 |
| P-005 | 数据存储周期 | MongoDB 全量保存 | 无自动过期 |
| P-006 | 消息队列积压 | 支持 ≥10000 条积压 | Redis Stream 缓冲 |
| P-007 | 批量写入 | 每批 100 条或间隔 5s | consumer.py 配置 |

### 4.2 安全性要求

| 编号 | 要求 | 说明 |
|------|------|------|
| S-001 | API 认证 | 数据接收接口需携带 X-API-Key 请求头 |
| S-002 | 数据完整性 | 每次上报计算 JSON 的 MD5 摘要，放在 X-Content-MD5 请求头 |
| S-003 | 传输加密 | 所有外部通信走 HTTPS（Nginx 反向代理 + 自签名证书） |
| S-004 | 微信登录鉴权 | 小程序端通过微信 jscode2session 获取 open_id |
| S-005 | 数据库隔离 | MySQL 仅监听本地 127.0.0.1 |

### 4.3 可靠性要求

| 编号 | 要求 | 说明 |
|------|------|------|
| R-001 | 数据不丢失 | Redis 缓冲 + 死信队列 + 本地文件缓存三级保障 |
| R-002 | 消费者断线重连 | consumer.py 自动重连 Redis |
| R-003 | 数据去重 | daily_summary 采用 `ON DUPLICATE KEY UPDATE` 幂等写入 |
| R-004 | 优雅退出 | consumer.py 和模拟器均实现信号处理，退出前刷新缓存数据 |

### 4.4 可维护性要求

| 编号 | 要求 | 说明 |
|------|------|------|
| M-001 | 容器化管理 | 模拟器以 Docker 容器运行，支持批量启停 |
| M-002 | CI/CD | Jenkins 自动从 Gitee 拉取代码部署，支持手动构建 |
| M-003 | 日志记录 | 各模块独立日志文件（server.log、consumer.log），支持在线查看 |
| M-004 | 配置外部化 | 数据库连接、API Key 等配置通过环境变量注入 |

### 4.5 用户体验要求

| 编号 | 要求 | 说明 |
|------|------|------|
| U-001 | 小程序首页加载 | 首次进入 ≤3s 展示数据 |
| U-002 | 数据自动刷新 | 首页每 30s 自动轮询最新数据 |
| U-003 | 下拉刷新 | 分析页支持下拉刷新历史数据 |
| U-004 | 空状态引导 | 未绑定设备时显示引导提示 |
| U-005 | 视觉设计 | 白色清新风格，AQI 等级颜色标识（绿/黄/橙/红/紫） |

## 5. 数据库要求

### 5.1 MongoDB — 原始时序数据

| 项目 | 值 |
|------|-----|
| 数据库 | `air_quality` |
| 集合 | `records` |
| 记录数 | 无上限（全量保存） |
| 主要查询 | 按 `device_id` 和时间范围查询 |

### 5.2 MySQL — 业务数据

| 表名 | 用途 | 数据量预估 |
|------|------|-----------|
| `users` | 微信用户信息 | 与小程序用户数一致 |
| `user_devices` | 用户设备绑定关系 | 用户数 × 平均设备数 |
| `user_favorites` | 用户收藏设备 | 同量级 |
| `user_alerts` | 用户报警阈值设置 | 同量级 |
| `devices` | 设备注册信息 | ≤50 条 |
| `daily_summary` | 日统计聚合数据 | 设备数 × 运行天数 |

### 5.3 Redis — 消息队列

| Key | 用途 | 说明 |
|-----|------|------|
| `data_stream` | 数据缓冲队列 | 实时数据 |
| `dead_letter_stream` | 死信队列 | 消费失败数据 |
| `simulator_stats` | 模拟器心跳 | Hash 类型 |

## 6. 限制与约束

| 编号 | 约束 | 说明 |
|------|------|------|
| C-001 | 服务器资源 | 1.6GB RAM，2 核 CPU，需控制模拟器数量 |
| C-002 | 模拟方式 | 当前基于 Docker 容器运行软件模拟器，非真实硬件设备 |
| C-003 | HTTPS 证书 | 使用自签名证书，所有请求需跳过 SSL 验证 |
| C-004 | 微信小程序 | 需配置微信小程序的 AppID 和 AppSecret |
| C-005 | AI 分析 | 依赖 DeepSeek API 外部服务，需有效 API Key |
| C-006 | 设备编码 | 设备预配置在 `device_config.json`，目前 7 个，需手动增删 |
